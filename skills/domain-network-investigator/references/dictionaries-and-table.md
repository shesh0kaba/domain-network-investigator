# Dictionary history, naming dates and the combined report

Treat a literal substitution dictionary as a first-class discovery source. Revisit known dictionary URLs when repeating an investigation. On fresh related domains, inspect linked custom scripts and inline data for another dictionary; do not execute downloaded code or guess undisclosed endpoints. Preserve exact URL, profile, snapshot ID, observation UTC, source-domain registration, raw SHA-256, parser/version, literal spelling, key, line/context and parse failures. Preserve old versions.

Compare each new snapshot against both the latest comparable version and the union of earlier versions **within the selected profile**. A first snapshot is a baseline, not an update. If the bytes match, record zero additions/removals. Distinguish added, removed, reappeared, changed spelling and newly observed on a different source. Compare dictionaries of different families only with an explicit compatibility note; an unrelated supplier dictionary must not silently become the team's vocabulary. A duplicate dictionary on a younger domain does not make its old entries new names.

`scripts/dictionary_diff.py` accepts profile-scoped JSON snapshots with `entries` containing literal `name` values and a `summary` containing `source_url`, `sha256`, `retrieved_at`, `registration_utc`. Supply previous versions chronologically. It preserves accents/punctuation and refuses cross-profile inputs. Separately check additions against the global brand registry and the team's non-dictionary observations: “new to this dictionary history” is not necessarily “new to the investigation.” Store this distinction.

For each actual new entry, immediately queue exact-name and evidenced-alias SEO searches, public advertising/landing discovery and linked-page validation. Keep the name if no SEO site was found. Never manufacture a working ad URL by substituting a dictionary word into an existing campaign URL: save source-code evidence and the absence of a verified ad instead.

The helper's `--registration-date-proxy` switch is opt-in; enable it only for the user-requested estimate described below. By default no naming-date proxy is emitted. Identical raw hashes with different extracted name sets cause an error: reconcile parser version, selected dictionary family and extraction context before comparing. The output must be a new file and must not overwrite source snapshots.

When the user requests registration-based naming dates, store `name_created_at_proxy` = registry registration timestamp of the new source domain where that entry was found, plus `proxy_source_domain`, source URL, source registration and `first_observed_at`. Label it **«Дата нейминга — расчётная, по регистрации домена-источника»**. Preserve actual precision and UTC. This implements the user's ranking heuristic; it does not prove historical creation on that date. Do not silently replace an established earlier observation with a newer clone's date. Keep multiple source observations, their proxies and contradictions. An unchanged dictionary yields no newly dated entries. If registration is unknown, keep the proxy null rather than substituting TLS/crawl time.

Use one cumulative main table: **Нейминг | Сайт в поиске / SEO-кандидат | Рекламные ссылки / источник нейминга | Регистрация домена | Связь и проверка**. Retain all previous name rows, domains, ad paths, unavailable domains and source-only names. Grouping by name is optional; if a name has several domains, give each domain its own date or subrow. Never mix ad-domain and SEO-domain dates without identifying which domain the date belongs to. Default to descending registration time of the row's domain; unknown dates last. If grouping, sort a group by its newest domain and label that rule. Preserve UTC timestamps in detail, even when showing dates compactly.

An ad cell must link the exact observed campaign/article/landing URL and name, or state “advertising link not found in these checks.” Distinguish a landing/CTA from a verified paid-ad placement. An indexed search result is not proof of Google ranking. Offer filters for new names/domains, source-only names, technical clusters and access failures. Keep broad passive IP queues and the full unverified dictionary downloadable or in a separate searchable catalogue; do not present them all as verified team assets.
